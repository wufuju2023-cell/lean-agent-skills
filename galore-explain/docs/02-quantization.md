# 02 · 量化与反量化：粒度、舍入、误差反馈

**这一篇讲什么.** `01-numbers.md` 讲了 int8 这个"容器"有多精确；这一篇讲怎么把权重**装进**这个容器、又怎么**拿出来**。看起来只是 `q = round(W/s)` 一行代码，但真正决定精度的不是这行代码，而是四个工程选择：一个 `absmax` 管多少个元素（粒度）、要不要在小数点外面先剪一刀（裁剪）、余数怎么处理（舍入）、以及上一次的余数要不要留到下一次（误差反馈）。这四个选择本项目都有实测，其中两个的结论与"教科书直觉"相反：裁剪在真实激活上**有害**，随机取整在反复折叠时**更差**。最后算清"先反量化再 GEMM"这笔账，以及为什么它必须被吃进内核。

**读完你会知道.** 为什么对称量化要求 0 能被精确表示；为什么组 32 的 0.535% 比每通道的 0.828% 好 1.55 倍而这个倍数可以用"32 个 vs 2048 个高斯样本的 absmax"精确解释；为什么在 `α = 0.8/0.6/0.5` 处裁剪会把 8.64% 变成 18.2/34.1/42.3%；为什么"SR 无偏"和"折叠时 RTN 更好"两句话同时成立；为什么实测里**误差反馈**才是那个把 26.2% 拉回 23.5% 的开关，而 SR/RTN 之争只是噪声；以及 SmoothQuant 那个恒等式为什么能白白把 13.23% 降到 1.49%。

> 记号沿用 `00-notation.md`：`W` 权重 `m × n`，`x` 输入 `n` 维，`s` 尺度，`q_max` 上界（int8 为 127），`Q(·)`/`deq(·)`，`⌊·⌉` 最近取整，`SR(·)` 随机取整，`Ŵ` int8 骨架，`P R` 低秩修正，`K` 折叠间隔，`η` 学习率。数字出处：〔`路径`: `键`〕= 落盘 JSON，〔`路径` §n〕= 报告正文，〔推导〕= 本篇自算（§9 脚本），〔UNVERIFIED〕= 找不到、不猜。

## 1. 两个算子

### 1.1 定义

对称量化只有两个算子。给定一个"组"（group）内的元素集合 `g`：

```text
absmax = max_{w ∈ g} |w|
s      = absmax / q_max                    （q_max = 127 for int8, 7 for int4）
Q(w)   = clamp(⌊w / s⌉, -q_max, q_max)     （量化：实数 -> 整数码）
deq(q) = q · s                             （反量化：整数码 -> 实数）
```

"组"就是共享同一个 `s` 的元素集合。**这个集合怎么划，是 §2 的主题**，它比算子本身重要得多。

### 1.2 为什么必须对称：0 要能被精确表示

非对称量化写成 `q = ⌊(w - zero)/s⌉`，多一个零点偏移 `zero`，能多榨出一点范围（比如全正的数据）。但本项目不能用它，原因只有一条：**神经网络里 0 是特殊值**。

MoE 的 token padding（容量不够时补 0，补出来的 GEMM 结果必须也是 0）、掩码（`deq(0) ≠ 0` 会漏出一个常数偏置）、剪枝留下的 0 权重（否则"剪掉"变成"换成一个小数"）——三条都要求 `deq(0) = 0`。

对称量化里 `Q(0) = 0`、`deq(0) = 0`，上面三条自动成立。代价是范围浪费一半（数据全正时只用 0…127），在本项目的权重上这个浪费可以忽略（权重本来就正负各半）。

### 1.3 往返误差

一次"量化再反量化"（round-trip）的误差 `e = deq(Q(w)) - w` 满足 `|e| ≤ s/2`，且在每个格点内近似均匀，于是

`RMS(e) = s / sqrt(12)`。

注意这个式子对**任何一个** `w` 都不成立（单个 `w` 的误差是确定的、有偏的），它只在"大量随机 `w`"上成立。这一点在 §4 会变得非常关键。

## 2. 粒度：一个 `absmax` 管多少个元素

### 2.1 三种粒度

| 粒度 | 一个 `s` 管多少元素 | 沿哪个方向切 | 硬件支持 |
|---|---|---|---|
| per-tensor | 整个矩阵 `m·n` | — | 支持（最粗） |
| per-output-channel | 一行 `n` 个 | 沿 `n`（输入维） | 支持（本项目的默认） |
| per-group | 一行里的连续 32 个 | 沿 `K`/`n` 切组 | **不直接支持**（见 `03-tensor-cores.md` §2） |

为什么切的方向是沿输入维（K）而不是沿输出维？因为 GEMM 的累加方向是 K。沿 K 切组意味着"每个输出元素由 `K/32` 个（`K=2048` 时 64 个）不同尺度的部分和拼起来"，这在硬件上要额外的 epilogue（见 03 篇）；沿输出维切（每行一个尺度）则正好对应"一行输出乘一个数"，可以融进 epilogue。

### 2.2 实测：0.828% vs 0.535%

在合成的高斯权重上（`randn × 0.02`，`kernels/moe_int8_gemm.py` 的 `[256, 1024, 2048]`；本篇 §9 用 4 个专家复跑到同样的两个数）测权重相对 RMS 误差：

| 粒度 | 相对 RMS 误差 | 出处 |
|---|---|---|
| per-output-channel（每行一个 absmax，2048 个数） | **0.828%** | 〔`kernels/sweep.json`: `int8_per_channel_rel` = 0.008276〕 |
| per-group-32（每 32 个数一个 absmax） | **0.535%** | 〔`kernels/sweep.json`: `int8_group32_rel` = 0.005346〕 |
| 比值 | **1.55×** | 0.008276 / 0.005346 = 1.548 |

在真实专家权重上（`bench/foldnoise.py`，`[1024, 2048]`，σ_W = 6.14e-3）同一件事是 0.565%〔`static_int8_g32`〕——数量级一致，具体值随张量不同在 0.5%–0.6% 之间。

### 2.3 1.55 倍从哪来：absmax 的统计学

§1.1 的阶跃公式说误差 ∝ 台阶 ∝ absmax。所以两种粒度的误差比 = 两个 absmax 的比。高斯样本的 absmax 是"n 个样本最大值的期望"，本地环境实测（§9 脚本，每次 20,000 组）：

| 组大小 n | absmax/σ 中位数 | 均值 |
|---|---|---|
| 32 | 2.30 | **2.35** |
| 2048 | 3.58 | **3.63** |

比值 `3.63/2.35 = 1.54`——与实测的 1.55 差 1%。把这两个数代进 `step = 2·absmax/255`：

`组 32: step = 2·2.36σ/255 = 0.0185σ -> RMS 0.535%`（实测 0.535%）；`每通道: 2·3.66σ/255 -> RMS 0.828%`（实测 0.828%）。

**注意这里的口径**：由实测误差反推出来的 absmax 是 `2.36σ`（32 个样本）与 `3.66σ`（2048 个样本），而不是有些教材写的 `2.5σ / 4.4σ`。后者是"最大值的分位数上界"；大量组做平均后，梯度误差由 absmax 的**均值**决定，所以数值更小。这一处是推导与数据唯一对不上的地方，用 2.36/3.66 就完全对得上（§9 脚本可复跑）。

### 2.4 字节账

尺度是要存的，所以粒度越细越费空间。对 `[m, n]` 矩阵：

`per-channel + fp32 scale = 1 + 4/n` B/参数；`per-group-32 + fp16 scale = 1 + 2/32 = 1.0625` B/参数。`gate_up` 的 `n = 2048` → 1.0020 B；`down` 的 `n = 512` → 1.0078 B；加权 1.0039 B → 32.21 B 参数占 32.34 GB。组 32 则是 34.22 GB（+1.9 GB）。**组 32 用 1.9 GB 内存买 1.55 倍精度**——很划算，但它在硬件上要付 2.4 倍的算力代价（`03-tensor-cores.md` §2），所以最终没被采用。

## 3. 裁剪：为什么这里反而更差

### 3.1 推导：裁剪用偏差换台阶

设原始 absmax 为 `A`。裁剪的做法是选一个 `α < 1`，用 `s = α·A/q_max`，把超过 `α·A` 的元素夹到边界上。于是：

- **台阶变小**：`step` 变成原来的 `α` 倍 → 落在范围内的元素误差按 `α` 缩小。
- **尾部变成偏差**：所有 `|w| > α·A` 的元素被压到 `α·A`，误差 = `|w| - α·A`，这部分是**系统性**的、不可通过多采样平均掉的。

总误差平方 ≈ `α²·(范围内的量化方差) + (尾部被裁掉那部分的偏差²)`。第一项随 `α` 减小而变小（台阶变细），第二项随 `α` 减小而变大（裁得更多）。**是否划算，取决于两项之比——而它随位宽变化。**

### 3.2 判别式：8 bit 上裁剪永远输

用 §9 的脚本在 400 万个 `N(0,1)` 样本上直接算（per-tensor absmax = 3.66σ）：

| `α` | 高斯 8 bit | 高斯 4 bit | 真实激活 8 bit（§3.3） |
|---|---|---|---|
| 1.0（不裁） | **0.98%** | 14.12% | **8.64%** |
| 0.8 | 2.43% | 11.70% | 18.2% |
| 0.7 | 4.51% | **11.39%** | — |
| 0.6 | 8.08% | 12.95% | 34.1% |
| 0.5 | 13.83% | 17.54% | 42.3% |

高斯两列是本篇自算〔推导，§9 脚本〕，最后一列是实测〔`kernels/act_quant_schemes.py`，§3.3〕。读法：

- **4 bit 有内点最优**（`α ≈ 0.7`，14.1% → 11.4%）。这才是"裁到 2.5σ"那条教科书建议的来源：台阶粗时，缩小台阶的收益大于裁尾巴的损失。
- **8 bit 单调变差**（0.99% → 2.44% → 13.9%）。量化收益正比于 `step ∝ 1/2^b`，尾巴偏差与位宽无关——**位宽越高，裁剪越亏**。所以那条建议来自 4-bit / per-tensor 时代，搬到 8-bit 组量化上不成立。
- 真实激活的绝对水平高得多（起点 8.64%，`α = 0.5` 时 42.3%），涨幅反而比高斯小（4.9× vs 14×）——因为它的基线已经被那串大通道抬高了，见 §3.4。

### 3.4 机制：重尾，而且不是"一个离群值"

同一个脚本打印：per-token 的 `absmax/rms` 中位数是 **38×**（docstring 记 `~39x`，同一次运行）。健康高斯是 `3.7×`。第一反应是"裁到 `0.5·absmax` = 19×rms，应该只切掉那几个极端通道，无害"——但实测 42.3%。这说明**尾巴不是一两个离群值，而是一串连续变大的通道**：`absmax/rms = 38` 只是最大值，5×–38× 这个区间里有大量通道有实际能量。

而它们带的是真信号：RMSNorm 之后 hidden 的"主体 + 若干巨大通道"结构，正是 MoE 的 gate/up 投影最敏感的地方。裁掉它们等于把功能上最重要的那部分能量丢掉。**结论：在本项目的激活上不要裁剪**——而且 §3.2 说明了，即使在没有重尾的高斯上，8 bit 也不该裁剪。

> **出处说明**：8.64 / 18.2 / 34.1 / 42.3 来自 `kernels/act_quant_schemes.py` 的 stdout；该脚本只 print 不落盘，仓库里没有对应 JSON。同脚本 docstring 记的是 `8.81%` 与 `~39x`（另一次运行，差异在单批次波动内）。**按"单专家、单批次"理解，不要当稳定常数**；稳的只有"裁剪使误差单调变大"（跨度 5 倍，远超批次波动）。

## 4. 舍入：RTN 与 SR

### 4.1 RTN 的锯齿与偏差

最近取整（round-to-nearest, RTN，half-to-even）把 `x = w/s` 映到最近的整数。它的误差是 `x` 小数部分的**确定性锯齿函数**：

即 `f = x - floor(x)` 时误差（单位：格点）为 `-f`（`f < 0.5`）或 `1-f`（`f ≥ 0.5`）。对固定的 `x`，`E[RTN(x)] = RTN(x) ≠ x`——**它是有偏的**。只有当 `x` 在一个格点内均匀分布时，偏差才平均成 0（这时 RMS = `1/sqrt(12)` 个格点）。训练里 `x` 的变化是**有方向的**（权重在往一个方向漂），所以偏差不会自动平均掉：这就是"RTN 会把更新方向符号化"的数学来源。

### 4.2 SR 无偏

随机取整（stochastic rounding）把 `x = n + f` 映成 `n+1` 的概率 `f`、`n` 的概率 `1-f`：

`E[SR(x)] = n(1-f) + (n+1)f = x`（无偏，逐元素成立），`Var[SR(x)] = f(1-f)`（格点²）。`f` 均匀时 `E[f(1-f)] = 1/6`，所以 `RMS(SR) = 0.408` 个格点，而 `RMS(RTN) = 0.289` 个格点。

**SR 无偏，但单次方差是 RTN 的 2 倍（RMS 1.41 倍）。** 这个 `1.41` 是 §4.4 的关键。

### 4.3 实测：反复折叠时 RTN 更好

`bench/foldnoise.py`：真实专家权重，每 50 步把累积更新折进量化存储，折 20 次，`lr = 1e-4`：

| 方案 | 权重相对误差 | 功能相对误差 |
|---|---|---|
| int8 组 32，RTN | **2.53%** | **2.53%** |
| int8 组 32，SR | **3.61%** | **3.61%** |

〔`bench/foldnoise.json`: `int8_g32_lr0.0001_k50_sr0` → 0.02530，`..._sr1` → 0.03615〕

SR 比 RTN 差 **1.43 倍**。这个数字几乎正好是 §4.2 的 `sqrt(2) = 1.414`。

### 4.4 为什么：折叠 = 舍入误差的随机游走

关键在于折叠的**递推结构**。设第 `f` 次折叠前存储值是 `Ŵ_f`，累积更新是 `ΔW_f`，那么本次的量化目标是 `Ŵ_f + ΔW_f`，而参考轨迹是 `W_ref + ΔW_f`。于是

`e_f = Ŵ_{f+1} - W_{ref,f+1} = (本次目标的舍入误差) + e_{f-1}`。

**误差是累加的**：每次折叠都把一个 `±0.5` 格点的舍入误差**加到**上一次的误差上，没有任何机制把它拉回来。折 `N` 次后

`RMS(e_N) = sqrt(N)·RMS(单次误差)`，即 RTN 为 `sqrt(N)·q/sqrt(12)`、SR 为 `sqrt(N)·q/sqrt(6)`。代进 `N = 20`、`q = 1.14e-4`、`σ_W = 6.14e-3`：

```text
RTN: sqrt(20)·1.14e-4/sqrt(12) = 1.47e-4 = 2.40% σ_W   （实测 2.53%）
SR : sqrt(20)·1.14e-4/sqrt(6)  = 2.08e-4 = 3.39% σ_W   （实测 3.61%）
```

两条都在 6% 左右对上（5.1% / 6.1%），比值 `sqrt(2)` 与实测 1.43 也对上。**所以"折叠时 RTN 更好"根本不是"RTN 偏差小"的故事，而是"SR 每次的方差更大"的故事**：在误差会累加的结构里，方差（`1/6` vs `1/12`）直接变成总量。

这也解释了另一条被 `DESIGN.md` §5.1 记为"反直觉"的现象：折叠间隔 10 / 50 / 200 步、lr 从 2e-5 到 3e-4，误差几乎不变（1.18% / 2.53% / 2.55%）。用上面的模型看：

- 只要 `lr ≫ q`，单次折叠的舍入误差恒为 `q/sqrt(12)`，与 `lr` 无关 → 误差只由**折叠次数** `N` 决定，与间隔无关。
- `lr = 2e-5 = 0.18q` 时，80% 的折叠根本没让存储跨过格点（`√(20×0.18)·0.289q` = 1.18%，正是实测值）→ 误差反而小。

**但这里必须指出一个实验设计问题**：`bench/foldnoise.py` 的内层循环里 `k` 只被用作标签，`dW = randn·lr` 与 `k` 无关——也就是说"每 50 步折一次"实际模拟的是"每一步都折一次"。所以"折叠间隔不影响误差"在这个实验里部分是**构造出来的**，不能当成物理结论。真正的间隔效应要靠"每次折叠前累积 `√k·η`"的模型来测，`kernels/quant_scheme_decision.py` 的 `fold_every` 参数也没改过这个耦合。**这是本系列发现的第一个实验缺陷，`06` 篇会给出修正后的实验设计。**

## 5. 误差反馈：真正的开关

### 5.1 递推

误差反馈（error feedback, EF）就是 delta-sigma 调制：**把这次舍入丢掉的余数记下来，加进下一次的目标**。

`e_t = W_target,t - deq(Q(W_target,t))`，下一次 `W_target,t+1 ← W_target,t+1 + e_t`。换成"存储 + 累加器"的写法（本项目的形态）：

```text
存 Ŵ（int8），累加器 A（高精度）
每次折叠：  T = deq(Ŵ) + A + e_prev ;  Ŵ ← Q(T) ;  e_prev ← T - deq(Ŵ)
```

### 5.2 实测：EF 把 26.2% 拉回 23.5%

`kernels/quant_scheme_decision.py`：`1024×2048` 矩阵，2000 步，每 25 步折叠，指标是**到最优点的相对距离**（不是权重误差），`|ΔW|/q ≈ 0.026`（lr = 1e-5 那一行）：

| 方案 | 到最优点的相对距离 | 相对 bf16 的惩罚 |
|---|---|---|
| bf16 主权重（天花板） | **23.528%** | — |
| int8 + RTN | **26.214%** | **+2.69 pp** |
| int8 + SR | 24.259% | +0.73 pp |
| int8 + RTN + EF | **23.542%** | **+0.014 pp** |
| int8 + SR + EF | **23.558%** | **+0.030 pp** |

〔`kernels/quant_scheme_decision.json`: `bf16_lr1e-05` = 0.235278、`rtn_lr1e-05` = 0.262136、`sr_lr1e-05` = 0.242591、`rtn_ef_lr1e-05` = 0.235424、`sr_ef_lr1e-05` = 0.235582〕

三个读数：

1. **有 EF 时 RTN 和 SR 的差别只有 0.016 pp**——可以忽略。所以"RTN vs SR"在**有残差累加器**的系统里根本不是问题。
2. **没有 EF 时，RTN 差 2.69 pp，SR 差 0.73 pp**。这里 SR 反而更好，因为它至少无偏（§4.2）。
3. **EF 把两者都恢复到 bf16 的水平**（0.014 pp / 0.030 pp）。这就是"误差反馈是活跃成分"的直接证据。

> 读表注意：`lr = 1e-5`、2000 步只走完 2% 的路程，所以绝对距离 23.5% 主要是"还没走到"，不是精度问题。**只能读方案之间的差**。同一个脚本在 `lr = 3e-5`（`|ΔW|/q = 0.077`）处给出 bf16 8.48% / RTN 8.85% / EF 8.52%，差值同向、量级一致。

### 5.3 权重度量与损失度量为什么不一致

同一个系统，两个度量给出两个结论：

| 度量 | RTN | SR | 谁更好 |
|---|---|---|---|
| 权重相对误差（`foldnoise.py`，无 EF） | 2.53% | 3.61% | RTN |
| 到最优点的距离（`quant_scheme_decision.py`，无 EF） | 26.21% | 24.26% | SR |

原因在于两个度量看到的误差**结构不同**：

- 权重度量 `‖Ŵ - W‖_F/‖W‖_F` 对误差的**大小**敏感，对**方向**不敏感。SR 的方差更大（`q/√6` vs `q/√12`），所以在这个度量下必然更差。
- 损失度量对"误差是否与梯度方向一致"敏感。RTN 的误差在**缓慢漂移**时表现为**滞后**：值还没跨过半个格点时存储不动，跨过时一次跳一格，于是存储平均落后真实值约 `q/2`，方向恒与漂移方向相反——等价于一个**恒定阻力**，每 `K` 步折叠都会把它重置一次，但紧接着又重新建立。SR 没有这种滞后（期望上不落后），只增加零均值噪声，而噪声在 SGD 里会被平均掉一部分。

**结论：能用权重度量解决的问题不要用损失度量，反之亦然。** 但最终决定必须用损失度量——因为训练优化的就是损失。这就是为什么 `quant_scheme_decision.py` 的 docstring 写着 "settle it with LOSS, not weight error"。本项目两条都测了，最后采用的是"EF/残差累加器"（`P R`），它对两个度量都无害。

## 6. SmoothQuant：把激活的离群值搬到权重上

### 6.1 恒等式

对每个**输入通道** `k` 取一个正数 `s_k`，做

`x' = x / s`（按通道除，`s` 是 n 维向量），`W' = W · diag(s)`（第 k 列乘 `s_k`），则 `W' x' = W diag(s) diag(s)^-1 x = W x`——恒等，逐元素精确。

量化 `x'` 和 `W'`、反量化、再相乘，得到的是 `deq(Q(W'))·deq(Q(x'))`，它近似等于 `Wx`。**关键在于：`s` 由我们自由选，而它改变了"谁更难量化"。**

为什么需要它：激活的 `absmax/rms = 38×`（§3.4），说明每行里有几个通道是离群值。`x/s` 把离群通道压下去，`W·diag(s)` 把对应列的权重放大——**离群值从激活侧搬到了权重侧**。而权重侧是 per-output-channel 量化（一行一个 absmax），它对"某一列整体变大"的容忍度比激活侧高得多。

### 6.2 实测

`kernels/smoothquant_probe.py`，真实专家 0 的 `gate_up [1024, 2048]` + 真实激活：

| 方案 | 激活误差 | 端到端功能误差 |
|---|---|---|
| 只量化权重（per-row），激活不动 | — | 0.83%（权重误差，见 §2.2） |
| 权重 + 激活都量化（per-token absmax），无平滑 | **8.64%** | **13.23%** |
| 同上 + SmoothQuant `α = 0.7` | **0.57%** | **1.49%** |

〔`kernels/smoothquant_probe.py` 输出；激活那一列同 `kernels/act_quant_schemes.py`。端到端 13.23% → 1.49% 是该次记录的读数。〕

激活误差降了 **15 倍**（8.64 → 0.57），端到端降了 **8.9 倍**（13.23 → 1.49）。注意端到端降得比激活少：因为剩下的误差里有权重那一份（权重列被放大后变难量化，见 §6.3），也有 `silu`/`down_proj` 这一级的放大。

### 6.3 `α` 的取舍曲线

`s_k = ch_k^α`，`ch_k` 是第 k 个输入通道在所有 token 上的 absmax。两端是：

`α = 0` 不平滑：激活侧最难（8.64%）、权重侧最容易（0.83%）；`α = 1` 完全搬过去：激活侧最容易、权重侧最难（列被放大 `ch_k` 倍，per-row absmax 随之暴涨）。

中间有一个最优。**记录的那次运行给 `α = 0.7` 最优（1.49%）**；但 `runs/B/REPORT.md` §6 里同一脚本的复跑给出 `1.74 / 0.73 / 0.92 / 1.76`（`α = 0 / 0.3 / 0.5 / 0.7`），最优点落在 `0.3` 附近。两次都是"单专家、单批次"估计，**所以"α = 0.7 最优"只能当工程默认值（框架里确实用的是 0.7），不能当稳健结论——这一点标 UNVERIFIED**。稳的结论只有一条：`α ∈ [0.3, 0.7]` 都远好于不平滑（1.5%–1.8% vs 13.2%）。

## 7. 反量化的代价

### 7.1 朴素路径：+227%

"先反量化成 bf16，再走普通 GEMM"看起来是零成本的。实测（`bench/bench7.py`、`bench/bench8.py`，单层专家块）：

| 路径 | 时间 | 相对纯 GEMM |
|---|---|---|
| bf16 权重直接 GEMM（地板） | 11.41 ms | — |
| 朴素 dequant + GEMM（torch） | **37.35 ms** | **+227%** |
| Triton dequant + GEMM | **14.69 ms** | **+29%** |

〔`bench/bench8.json`: `gemm_ms` = 11.411、`naive_e2e_ms` = 37.345、`triton_e2e_ms` = 14.687〕

为什么朴素路径贵 3.3 倍？单独的 dequant 就要 **27.48 ms**〔`bench8.json`: `torch_dequant_ms`〕。这段时间花在**流量**上：

`[256, 1024, 2048]` 的 int8 存储 = 0.537 G 元素 = 0.537 GB；`q.float()` 造出的 fp32 临时量 = **2.147 GB**。理论必需流量（读 0.54 + 写 2.15 + 再读 2.15）= 4.84 GB → 7.6 ms @637 GB/s；`DESIGN.md` §5.2 的 3.2 GB 口径给 5.0 ms。实测 27.48 ms = 后者的 5.5 倍，有效带宽只有 ~98 GB/s。

**根因是 `q.float()` 会 materialize 一个 2.15 GB 的 fp32 张量**：它把"位宽 1 字节"的存储膨胀成 4 字节，然后 GEMM 再读一遍、再转成 bf16。三次全量访存，每次都不命中 L2。这不是 kernel 写得差，是**数据被放大**了。

### 7.2 Triton 版：+29%

手写一个 Triton pass，让它在搬运的同时完成 int8→bf16 的转换，不落 fp32 中间量：

| 指标 | torch 版 | Triton 版 | 比值 |
|---|---|---|---|
| dequant 单独 | 27.48 ms | **3.60 ms** | 7.6× |
| dequant + GEMM | 37.35 ms | 14.69 ms | 2.5× |
| 有效带宽 | ~98 GB/s | **447 GB/s**（1.61 GB 必需流量 / 3.60 ms） | 4.6× |

〔`bench/bench8.json`: `torch_dequant_ms` = 27.476、`triton_dequant_ms` = 3.602、`speedup` = 7.63；带宽一列是除法：1.61 GB / 3.602 ms = 447 GB/s〕

3.60 ms 已经到 HBM 的 70%（637 GB/s 是拷贝带宽）。**也就是说 dequant 这条路的极限就是"把 1.61 GB 搬一遍"，再怎么优化也省不掉这 3.60 ms。**

### 7.3 结论

三个层次的答案，代价递减：

`朴素 dequant + GEMM` 37.35 ms（+227%，不可接受）→ `融合进 bf16 GEMM` 14.69 ms（+29%，可接受但仍在搬 bf16 流量）→ `根本不 dequant` ~3.13 ms（−73%，要写原生 int8 GEMM）。

第三行是本项目最终的方向：**权重的存储形态是 int8，前向也应该在 int8 里做**。一旦这么做，反量化这条开销连同它需要的 1.61 GB 显存缓冲一起消失。`03-tensor-cores.md` 讲硬件上能不能做，`06` 篇讲本项目的装配。

## 8. 本项目的决策表

| 选择 | 结论 | 为什么 | 代价 |
|---|---|---|---|
| 对称 vs 非对称 | **对称** | 0 必须精确（padding / mask） | 范围浪费一半，可接受 |
| 粒度 | **per-output-channel**（硬件允许的最细） | 组 32 的 int8 内核慢 2.4× | 0.828% 而非 0.535%（+1.9 GB 换 -0.29 pp，不值） |
| 激活侧 | **per-token absmax + SmoothQuant α=0.7** | 8.64% → 0.57% | 权重列被放大，权重误差上升（未单独量化记录） |
| 裁剪 | **不裁剪** | 激活重尾，`absmax/rms = 38×` | 无 |
| 舍入 | **RTN（折叠时）** | SR 方差 2 倍，误差会累加 | 需配误差反馈 |
| 误差反馈 | **必须有**（`P R` 累加器） | 26.21% → 23.54%，回到 bf16 水平 | 一个 `r × n` 的高精度累加器 |
| 反量化 | **不做**（原生 int8 GEMM） | +227% / +29% / −73% | 要自己写 int8 grouped GEMM |

## 9. 复现脚本

```python
"""02 篇：粒度、折叠的随机游走、SmoothQuant 恒等式。CPU 即可。"""
import numpy as np
rng = np.random.default_rng(0)
NE, N, K = 4, 1024, 2048
W = (rng.standard_normal((NE, N, K)) * 0.02).astype(np.float32)

# ---------- (a) 粒度 ----------
def q(W, g=None, qmax=127):                       # g=None -> 每行一个 absmax
    if g is None:
        s = np.abs(W).max(-1, keepdims=True).clip(1e-12) / qmax
        return np.round(W / s).clip(-qmax, qmax) * s
    Wg = W.reshape(*W.shape[:-1], K // g, g)
    s = np.abs(Wg).max(-1, keepdims=True).clip(1e-12) / qmax
    return (np.round(Wg / s).clip(-qmax, qmax) * s).reshape(W.shape)

rel = lambda A, B: np.sqrt(((A - B) ** 2).mean()) / np.sqrt((B ** 2).mean())
e1, e2 = rel(q(W), W), rel(q(W, 32), W)
print(f"(a) per-channel {e1*100:.3f}%  group-32 {e2*100:.3f}%  ratio {e1/e2:.2f}x"
      f"   [实测 0.828 / 0.535 / 1.55]")
for n in (32, 2048):                               # absmax 的统计
    m = np.abs(rng.standard_normal((20000, n))).max(-1)
    print(f"    |N| 取 {n:5d} 个: absmax 均值 {m.mean():.2f} sigma")

# ---------- (b) 折叠 = 随机游走；RTN vs SR vs EF ----------
M2, N2, G, lr, folds = 256, 512, 32, 1e-4, 20
wt = (rng.standard_normal((M2, N2)) * 6.14e-3).astype(np.float32)
amax = np.abs(wt.reshape(M2, N2 // G, G)).max(-1, keepdims=True)
s = np.repeat((amax / 127).reshape(M2, N2 // G), G, axis=1)
step = (2 * amax / 255).mean()
print(f"(b) 组内 absmax {amax.mean()/6.14e-3:.2f} sigma, 台阶 {step:.3e}")

def rnd(x, sr):
    x = np.clip(x, -127.5, 127.5)
    if not sr:
        return np.clip(np.round(x), -127, 127)
    fl = np.floor(x)
    return np.clip(fl + (rng.random(x.shape) < (x - fl)), -127, 127)

for sr, ef in ((False, False), (True, False), (False, True), (True, True)):
    ref, resid = wt.copy(), np.zeros_like(wt)
    c = rnd(wt / s, sr)
    for _ in range(folds):
        dW = (rng.standard_normal(wt.shape) * lr).astype(np.float32)
        ref += dW
        tgt = c * s + dW + (resid if ef else 0)
        cn = rnd(tgt / s, sr)
        resid = tgt - cn * s if ef else resid
        c = cn
    print(f"    {'SR' if sr else 'RTN'}{'+EF' if ef else '   '}: {rel(c*s, ref)*100:5.2f}%"
          f"   [实测 RTN 2.53 / SR 3.61 / EF ~0.5]")
print(f"    解析 sqrt(20)*q/sqrt(12)/sigma = {np.sqrt(20)*step/np.sqrt(12)/6.14e-3*100:.2f}%")

# ---------- (c) 裁剪：高斯上的 α 曲线 ----------
x = rng.standard_normal(1 << 20)
for b in (8, 4):
    qm = 2 ** (b - 1) - 1
    for a in (1.0, 0.8, 0.7, 0.6, 0.5):
        s = 2 * 3.66 * a / (2 ** b - 1)
        print(f"(c) {b}bit a={a}: "
              f"{np.sqrt((((np.clip(np.round(x/s), -qm, qm)) * s - x) ** 2).mean())*100:5.2f}%")

# ---------- (d) SmoothQuant 恒等式 ----------
X = rng.standard_normal((64, K)).astype(np.float32)
y0 = X @ W[0].T
for a in (0.3, 0.7, 1.0):
    sk = np.abs(X).max(0) ** a
    print(f"(d) alpha={a}: max|y'-y|/max|y| = "
          f"{np.abs((X/sk) @ (W[0]*sk).T - y0).max()/np.abs(y0).max():.1e}")
```

实测输出（本地环境）：`(a) per-channel 0.826% group-32 0.535% ratio 1.55x`；`(b) RTN 2.74% / SR 3.69% / RTN+EF 1.21% / SR+EF 1.45%`（解析 2.36% / 3.33%）；`(c) 8bit a=1.0:0.98% a=0.8:2.43% a=0.5:13.83%`、`4bit` 在 `a=0.7` 最低（11.39%）；`(d)` 各 α 均为 `1e-7` 量级。§5.2 的损失度量表直接读 `kernels/quant_scheme_decision.json`，不再重跑。

## 本篇要点

1. 对称量化的定义只有 `s = absmax/q_max`、`Q = ⌊w/s⌉`、`deq = q·s`；**必须对称是因为 0 要精确**（padding / mask / 剪枝）。
2. 粒度决定误差：每通道 0.828%、组 32 0.535%，差 1.55 倍，正好等于"2048 个 vs 32 个高斯样本 absmax"之比（3.66σ vs 2.36σ）。组 32 多花 1.9 GB 内存，但在硬件上慢 2.4 倍。
3. 裁剪在真实激活上**有害**：8.64% → 18.2 / 34.1 / 42.3%（α = 0.8/0.6/0.5）。原因是 `absmax/rms = 38×` 的重尾，尾巴带真信号，不是噪声。
4. RTN 有偏、SR 无偏但方差 2 倍（`q/√6` vs `q/√12`）。反复折叠时误差按 `√N` 累加，所以 SR 差 1.41 倍——实测 3.61/2.53 = 1.43，公式预测 1.414，对上了。
5. **误差反馈才是开关**：`|ΔW|/q ≈ 0.026` 时 RTN 26.214% vs bf16 23.528%，加 EF 后 23.542%（RTN）/ 23.558%（SR），几乎完全恢复。此时 RTN 与 SR 的差别只有 0.016 pp。
6. 权重度量与损失度量会给出相反结论（RTN 在权重上更好、SR 在损失上更好），因为前者只看误差大小、后者看误差方向。**决策必须用损失度量**，而本项目最后选了同时对两者无害的第三条路：残差累加器。
7. SmoothQuant 是恒等式 `W diag(s)·diag(s)^-1 x = Wx`，把激活离群值搬到权重列：激活误差 8.64% → 0.57%，端到端 13.23% → 1.49%。`α` 的最优点两次运行不一致（0.7 vs 0.3），标 UNVERIFIED。
8. 反量化的代价是流量：朴素 torch 版 +227%（`q.float()` 造 2.15 GB fp32 临时量），手写 Triton +29%（3.60 ms，447 GB/s）；正解是**不要反量化**，直接 int8×int8。
