# 03 · 张量核与稀疏张量核：硬件到底允许你做什么

**这一篇讲什么.** 前两篇讲的是"数字怎么存"，这一篇讲"数字怎么算"。GPU 上真正干矩阵乘法活的不是 CUDA core，而是张量核（tensor core）：一个只认识"小矩阵块相乘再累加"这一件事的专用电路。它的峰值随 dtype 变化（本地环境 bf16 118 TFLOP/s、int8 206 TOPS），而这个差别不是营销数字，是"一条指令一次能乘多少个元素"的硬件事实。更重要的是一串**约束**：int8 张量核要求两个操作数都是 int8、累加器是 int32，于是"每个尺度只能乘一次"——这一条直接判掉了组 32 的权重尺度。再往下是布局陷阱（同样的 `torch._int_mm`，B 列主序 206 TOPS、行主序 50 TOPS）、roofline 与"`M < 137` 必然带宽受限"这条规则，最后是 2:4 稀疏张量核在这个卡上的实测现实：**规格 2 倍，实测最好 1.47 倍，int8 从来没有超过稠密**。

**读完你会知道.** 张量核一条 `mma` 到底算什么、为什么 int8 的峰值是 bf16 的 2 倍；为什么 int8 的尺度只能挂在输出通道上、而组 32 要付 2.4 倍算力代价；为什么"`nn.Linear` 的权重天生就是列主序"这句话是对的、以及踩错会掉 4 倍；怎么用算术强度推出 `M < 137` 这条线、以及为什么本项目 harness 的 `M = 128` 正好卡在这条线上、139.4 TOPS 就是那个形状的天花板；2:4 稀疏为什么在 sm86 上没有可用路径、以及"静态 2:4 当稠密 K/2 GEMM 打"这条 1.54–1.88 倍的偏方要用多少精度去换。

> 记号沿用 `00-notation.md`：`W` 权重 `m × n`，`x` 输入，`G` 梯度，`Ŵ` int8 骨架，`s` 尺度，`T` 基刷新间隔。本篇额外用到 GEMM 的 `M`（行数/token 数）、`K`（收缩维）、`N`（输出维）；注意这里的 `M/N/K` 是 GEMM 的形状记号，与 `00` 号文档里 `m × n` 权重矩阵的 `m, n` 是同一件事的两种写法（`M` = token 数，`N` = 输出通道数，`K` = 输入通道数），`K` 在 `00` 里另指折叠间隔，本篇凡出现"`K` 折叠"时会写明。

> **数字出处约定.** 〔`路径`: `键`〕= 落盘 JSON；〔`路径` §n〕= 报告正文；〔推导〕= 本篇自算（§7 脚本）；〔UNVERIFIED〕= 找不到、不猜。

## 1. 张量核到底算什么

### 1.1 一条 `mma` 指令

一个张量核的基本动作叫 `mma`（matrix multiply-accumulate）：

```text
D = A · B + C
A: 16 × 16 的 bf16        B: 16 × 8 的 bf16        C, D: 16 × 8 的 fp32
```

也就是一条指令做 `16 × 8 × 16 = 2048` 次乘加 = 4096 flops，全部在同一个时钟周期族里完成，操作数在寄存器里、不需要经过 shared memory。整块 GPU 的峰值就是

```text
峰值 flops/s = (每个 SM 的 mma 吞吐) × SM 数 × 时钟
```

本地环境是 GA102（sm86），68 个 SM。bf16 的实测峰值 **118 TFLOP/s**〔`STATE.md` §1；`bench/roofline.py` 产出，该 JSON **未落盘**〕，规格 119——基本打满。fp16 是 116 TFLOP/s〔同表〕，与 bf16 同一条指令形状，所以同速。

### 1.2 为什么峰值随 dtype 变

关键在每条指令的 `K`（收缩深度）：

| dtype | 指令形状 | 每条指令的乘加数 | 相对 bf16 |
|---|---|---|---|
| bf16 | `m16n8k16` | 16×8×16 = 2048 | 1× |
| fp16 | `m16n8k16` | 2048 | 1× |
| int8 | `m16n8k32` | 16×8×32 = 4096 | **2×** |

int8 的 `K` 是 32 而不是 16，所以同一条指令干两倍的活。实测比值 `206/118 = 1.75`（规格 `238/119 = 2.0`），差的 12% 是调度与 bound 效应。fp8 在 Hopper 上也是 `k32`，但 **sm86 没有 fp8 张量核**，本地环境的 fp8 只能先转 bf16 再算，不在路线图里。

### 1.3 bf16 为什么必须 fp32 累加

`A·B` 里每个乘积是 `bf16 × bf16 → bf16`（8 位有效数字），但 `C` 和 `D` 是 **fp32**。原因：GEMM 要累加 `K` 次（本项目 `K = 2048`），如果累加器也是 bf16，每次加都舍入到 8 位有效数字，2048 次之后相对误差约 `sqrt(2048)·2^-8 = 0.18`——结果完全不可用。fp32 累加把每次舍入压到 `2^-24`，2048 次后 `sqrt(2048)·2^-24 = 2.7e-6`，可以忽略。

**这就是"bf16 张量核"的准确含义：输入 bf16、乘积 bf16、累加 fp32。** 少了后半句，这个格式在训练里根本不能用。

## 2. int8 的两条硬约束

### 2.1 两个操作数都必须是 int8，累加器必须是 int32

int8 张量核的指令是 `mma.s8.s8.s32`：A、B 是 int8，C/D 是 int32。它**没有**"int8 输入、fp32 累加"的变体（那是 Hopper 的 fp8 才有的）。推论：

```text
acc = Σ_k a_k · b_k        a_k, b_k ∈ [-128, 127]，acc 是 int32
|acc| ≤ K · 127 · 127 = K · 16129
不溢出条件：K ≤ 2^31 / 16129 ≈ 133,000
```

本项目 `K` 最大 2048，`|acc| ≤ 3.3e7`，远小于 `2^31`——**安全，而且完全精确**：int32 累加没有任何舍入。这一点值得强调：int8 GEMM 的唯一误差来源是输入量化，算术本身是精确的；bf16 GEMM 反而每次累加都在舍入。

### 2.2 尺度只能乘在 epilogue 上

现在把尺度放回去。我们要算的是

```text
y[m, n] = Σ_k (a[m,k]·sx[m]) · (w[n,k]·sw[n])
        = sx[m] · sw[n] · Σ_k a[m,k]·w[n,k]
```

`sx[m]` 只依赖行、`sw[n]` 只依赖列，**都能提到求和号外面**。所以 epilogue 只需要两次乘法（一个 `M×1`、一个 `1×N`，本项目的 Triton 内核把它们融成一次 `acc * (xs[:,None] * ws[None,:])`，见 `kernels/moe_int8_gemm.py` 的 `epi=1` 分支）。

但如果尺度是**沿 K 分组**的（组 32，`s[k//32]`），它就**进不了求和号外面**：

```text
y[m, n] = Σ_k a[m,k] · w[n,k] · sw[n, k//32]
```

这个和必须拆成 `n_groups` 个部分和，每个部分和乘自己的尺度再相加。而 int8 张量核的累加链是 int32 寄存器——**一旦要在中间乘一个浮点尺度，就必须把部分和搬出张量核、转成 fp32、乘、再加回去**，累加链断掉。实测代价（`runs/B/kg32.json`，同一内核改成"K 循环按 32 分组"）：

| 配置 | 每通道尺度 | 组 32 尺度 | 损失 |
|---|---|---|---|
| BM128/BN256/BK128 | 176.3 TOPS | 73.4 TOPS | 2.40× |
| BM128/BN128/BK128 | 167.3 TOPS | 63.9 TOPS | 2.62× |
| BM128/BN256/BK64 | 176.3 TOPS | 87.4 TOPS | 2.02× |

〔`runs/B/kg32.json` 的 `pc_tops` / `g32_tops`；`runs/B/REPORT.md` §2.3 记为"2.0–2.4x loss"〕

而它买到的精度只是 `0.828% → 0.535%`（1.55 倍，见 `02-quantization.md` §2.2）。**用 2.4 倍算力换 1.55 倍权重精度，不划算**——这是本项目选择 per-output-channel 的唯一理由。

### 2.3 于是精度的补救只能从别处来

既然硬件只允许每通道尺度，`0.828%` 的权重误差就是硬件的底噪。本项目的补救是两条，都不在 GEMM 里：

- **SmoothQuant**：把激活的离群通道搬到权重列上（`02-quantization.md` §6），代价是权重列被放大、误差上升。零运行时成本（离线折进存储）。
- **低秩残差 `P R`**：把"刚发生但还没写进 int8 的更新"放在 bf16 里精确保留（`02` §5），让精度损失不进前向。

## 3. 布局陷阱：同一行代码 4 倍差距

### 3.1 实测：50 vs 206

`torch._int_mm(a, b)` 看起来只接受两个 int8 矩阵。实测（`bench/bench9.py`，8192³）：

| B 的布局 | TOPS | 派发到的内核 |
|---|---|---|
| 行主序（`b` 本身，stride `(8192, 1)`） | **50.3** | legacy 非张量核路径 |
| 列主序（`b.t()`，stride `(1, 8192)`） | **205.8** | `cutlass_80_tensorop_i16832gemm_s8` |

〔`bench/bench9.json`: `sq_rowmajor` = 50.276、`sq_colmajor` = 205.830；`DESIGN.md` §11 记录了这个错误的第一版读数 47 TOPS〕

**它不报错，只是慢 4 倍。** 第一次测出 47 TOPS 的人（就是本项目的第一版文档）因此得出了"int8 张量核不可用"的错误结论，直到发现布局问题。

### 3.2 为什么列主序才对

张量核的 B 操作数按 `k` 方向取片段：一条 `mma` 要 `B[k0:k0+32, n0:n0+8]`。如果 B 沿 `k` 的步长是 1（列主序），这 32 个元素在内存里连续，一次 32 字节的合并读就够；如果沿 `k` 的步长是 `N`（行主序），每个元素都要单独发一次跨步访问、只取 1 字节。硬件路径（cutlass 的 `i16832` kernel）只对前者做了向量化。

### 3.3 `nn.Linear` 的权重天生就是列主序

这是本项目最"免费"的一件事。PyTorch 的 `nn.Linear` 把权重存成 `[out, in] = [N, K]` 行主序，stride 是 `(K, 1)`。而 GEMM 要的 B 是 `[K, N]`，即 `Wᵀ`，它的 stride 是 `(1, K)`——**正好是列主序**：

```text
>>> W = torch.empty(1024, 2048, dtype=torch.int8)   # nn.Linear 权重 [N, K]
>>> W.stride()
(2048, 1)                                           # 行主序
>>> W.T.stride()
(1, 2048)                                            # 列主序 —— 正是 cutlass 要的
```

所以 checkpoint 的原始布局不用动，直接 `_int_mm(x, W.T)` 就走快路径。反之，如果你为了"整理布局"先做了 `W.T.contiguous()`（变成 `[K, N]` 行主序，stride `(N, 1)`），反而掉回慢路径。**这是本项目里最容易犯又最贵的一个错。**

## 4. Roofline 与 `M < 137` 规则

### 4.1 算术强度

对一个 `[M, K] × [K, N]` 的 GEMM，flops 是 `2MKN`。如果权重（`K·N` 字节，int8）只读一次、激活（`M·K` 字节）也只读一次，那么最少的访存是 `K·N + M·K` 字节（输出先忽略）。算术强度（arithmetic intensity, AI）是

```text
AI = 2MKN / (KN + MK) = 2MN/(N + M)
```

当 `M ≪ N`（本项目 `M = 128, N = 1024`）时，`N + M ≈ N`，于是

```text
AI ≈ 2M  flops/byte
```

**每多一个 token，就多摊 2 个 flops/byte。** 这是权重流主导（weight-stream bound）区的全部内容。

### 4.2 屋脊点

把峰值算力和带宽相除，得到一个"转折点"：

```text
规格：    208 TOPS / 760 GB/s = 274 flops/byte
本地环境实测： 205.8 TOPS / 637 GB/s = 323 flops/byte
```

〔`00-notation.md` §0.5 用的是规格口径 274；`DESIGN.md` §1 与 `runs/B/REPORT.md` §1 也是 274。用本地环境**实测**的 637 GB/s 与 206 TOPS 会得到 323——两个都对，只是口径不同：规格带宽永远达不到，用实测带宽算出来的屋脊点更高、更接近真实行为。〕

`AI < 屋脊点` → 带宽受限；`AI > 屋脊点` → 算力受限。代入 `AI = 2M`：

```text
2M < 274  ->  M < 137        （规格口径，DESIGN.md 与 runs/B/REPORT.md 用的）
2M < 323  ->  M < 162        （本地环境实测口径）
```

**这就是 `M < 137` 规则的来历：任何 int8 GEMM，只要 token 数（每个专家）少于 137，就必然跑不到峰值，因为它在等内存。**

### 4.3 实测：139.4 TOPS 就是那个形状的天花板

本项目的 harness 每次对一个 2048-token 序列调用一次 MoE：`2048 个 token × 8 个激活专家 / 256 个专家 = 64 token/专家`，容量 2.0 后补齐到 `M = 128`〔`runs/B/REPORT.md` §1、§3〕。算这条形状的地板：

```text
搬动量（每专家）= 权重 2.10 MB + 激活 0.26 MB + bf16 输出 0.26 MB = 2.62 MB
256 个专家      = 671 MB
地板时刻        = 671 MB / 637 GB/s = 1.05 ms      （报告写 643 MB / 1.01 ms，是 MiB 口径）
算力地板        = 137.4 GFLOP / 205.8 TOPS = 0.67 ms
-> 带宽地板 > 算力地板，这个形状是带宽受限的
```

实测 0.99 ms → 139.4 TOPS〔`runs/B/REPORT.md` §2.1〕。**它比用拷贝带宽算的地板还快一点**，因为这份流量 ~90% 是读、10% 是写，而 637 GB/s 是读写各半的拷贝带宽。换句话说：`139.4 TOPS` 不是内核没写好，是这个形状的物理上限。

同一内核在更大的 `M` 上：

| M（token/专家） | 实测 TOPS | 占峰值 206 | 状态 |
|---|---|---|---|
| 128 | **139.4** | 68% | 带宽受限（地板 1.05 ms，实测 0.99 ms） |
| 256 | **192.2** | 93% | 过线，接近峰值 |
| 512 | **189.6** | 92% | 算力受限 |
| 1024 | 189.3 | 92% | 算力受限 |
| 2048 | 186.3 | 90% | 算力受限 |

〔`runs/B/REPORT.md` §2.2〕

### 4.4 "token/专家 直接决定可达 TOPS"

上一张表就是这句话的全部证据。而 **token/专家 = tokens_per_step × 8 / 256 = tokens_per_step / 32**（每个 token 选 8 个专家、共 256 个专家，均匀时每个专家拿 `tokens/32` 个）。于是：

```text
tokens/step = 4096   -> 128 token/专家  -> 带宽受限，~139 TOPS
tokens/step = 16384  -> 512 token/专家  -> 算力受限，~190 TOPS
```

这条链子把"batch size"和"张量核利用率"直接绑在一起。它也解释了为什么 `DESIGN.md` 把 16384 定为平衡点：再小，GEMM 在等内存；再大，激活爆显存（`DESIGN.md` §3.3）。

## 5. 2:4 结构化稀疏

### 5.1 什么是 2:4

每 4 个连续元素里保留 2 个（通常保留绝对值最大的 2 个），其余置 0。硬件端叫 `mma.sp`：A 或 B 操作数带一份**元数据**（metadata）告诉它"这 4 个里哪 2 个非零"，然后只算那 2 个。

| 项 | bf16 | int8 |
|---|---|---|
| 值（2/4） | 1.0 B/元素 | 0.5 B/元素 |
| 元数据（理论 2 bit/4 元素） | 0.0625 B | 0.0625 B |
| **打包率（相对稠密）** | **0.5625** | 0.5625（理论） |
| cuSPARSELt 实测打包率 | **0.5625** | **0.75**（元数据花掉 1 B/4 元素） |

〔`research/sparse/feasibility.md` §5，实测 `_cslt_compress` 的打包尺寸〕

int8 的 0.75 是硬件库的实现细节：它用了整整一字节存"哪 2 个非零"（其实只有 6 种可能，3 bit 就够），所以元数据是它索引的那份数据的一半大。

### 5.2 实测：bf16 1.47 倍，int8 从来没赢

`research/sparse/feasibility.md`（cuSPARSELt 0.8.1 + torch 2.13）在**唯一可用**的路径（`torch._cslt_sparse_mm`）上测：

| 项 | 结果 |
|---|---|
| bf16 最好成绩 | **154.1 TFLOP/s = 1.47×**（`in_proj_qkv` 2048→8192，`alg_id=3`） |
| bf16 区间 | 1.16–1.47×，**从不到 2×** |
| int8 @ M=512 | **0.12×**（0.301 ms vs 稠密 0.036 ms） |
| int8 @ M=65536 | 0.98×（接近打平但**从未超过**） |
| 我们自己的 int8 grouped kernel @ M=512 | 180 TOPS，比 cuSPARSELt int8 快 **21×** |
| Triton 的 `mma.sp` | **没有 API**：triton 3.7.1 只有 `tl.dot` / `tl.dot_scaled` |
| 反向传播 | **不支持**：`derivative for aten::_cslt_sparse_mm is not implemented` |

int8 的稀疏路径在 sm86 上为什么这么差，`feasibility.md` 给的解释是：cuSPARSELt 的 int8 kernel 是按大 `M` 调的，本项目 `M = 128` 的形态下它连稠密 kernel 都不如；而且**没有批量/分组 API**，256 个专家要发 256 次调用——这正是 0.12× 的来源。

### 5.3 唯一真正可用的路径：静态 2:4 当稠密 K/2 GEMM 打

如果掩码（mask）是**固定的、每个输出通道相同的**，那么"2:4 稀疏 GEMM"等价于"K 减半的稠密 GEMM"：

```text
y = Σ_{k kept} a_k w_k = A[:, kept] @ W[:, kept]     （不需要任何稀疏指令）
```

代价是 50% 的存储、零元数据、数值上完全精确（除了 bf16 累加）。实测：

| 场景 | 稠密 | 静态 2:4 | 增益 |
|---|---|---|---|
| bf16 前向 `in_proj_qkv` | 114.4 TFLOP/s | **198.3** | 1.73× |
| bf16 全 fwd+bwd 三件套 | 108.7 | **204.4** | **1.88×** |
| grouped int8 `gate_up` | 180.2 TOPS | **303.0** | **1.68×** |
| grouped int8 `down` | 125.1 | **173.2** | 1.38× |
| int8 按 flops 加权 | — | — | **1.54×** |

〔`research/sparse/feasibility.md` §2a/§2b/§4〕

但精度代价是致命的（`research/sparse/accuracy.md`，真实权重 + 真实激活）：

| 方案 | 功能误差（层输出） |
|---|---|
| int8，不稀疏（现状） | **0.7–1.5%** |
| 2:4 按幅值，`gate_up` | **23.1%** |
| 2:4 按幅值，`down_proj` | **32.8%** |
| 2:4 固定掩码 | **62–68%** |

原因是这些权重**没有可利用的稀疏结构**：每 4 个一组，top-2 保留的能量占比 0.8684，而 iid 高斯是 0.8678——统计上和噪声无法区分。所以 2:4 不是"发现稀疏"，是"硬剪掉 13% 的能量"。

| int8 MoE 真实形状（扁平化 M=131072） | 175.0 / 125.5 TOPS | `bench/bench9.json` | 天花板；同形状 bf16 只用 111.6 |
| int8 + 组 32 尺度（内核内） | 73.4–87.4 TOPS | `runs/B/kg32.json` | 否：2.4 倍代价换 1.55 倍精度 |
| int8 grouped，M=128（本项目的真实形状） | **139.4 TOPS** | `runs/B/REPORT.md` §2.1 | 带宽上限，接受 |
| 2:4 稀疏，bf16（cuSPARSELt） | 154.1 TFLOP/s = 1.47× | `research/sparse/feasibility.md` | 否：不到 2×，且要手写 autograd |
| 2:4 稀疏，int8（cuSPARSELt） | 0.12× @ M=512，从未 > 1× | 同上 | **否，彻底** |
| 2:4 静态掩码当稠密 K/2 | 1.54–1.88× | 同上 | 速度可行但精度 23–68%，否 |
| fp8 张量核 | 本地环境无此硬件 | — | 不在路线图 |

一句话：**这张卡上真正满速的只有两件事——bf16（118 TFLOP/s）和"布局正确的 int8"（206 TOPS）。** 其余的（int4、fp8、2:4）要么没有硬件，要么实测拿不到规格的收益。

## 本篇要点

1. 张量核一条 `mma` 是"小矩阵块相乘再累加"：bf16 是 `m16n8k16`、int8 是 `m16n8k32`，`K` 差 2 倍，所以 int8 峰值是 bf16 的 2 倍（实测 206 vs 118）。
2. bf16 张量核 = bf16 输入 + **fp32 累加**。累加器若是 bf16，`K = 2048` 的误差会到 0.18，不可用。
3. int8 要求两个操作数 int8、累加 int32，且 `K ≤ 133k` 不溢出。int32 累加是**精确**的：int8 GEMM 的唯一误差来自输入量化。
4. 尺度只能乘在 epilogue：`sx[m]·sw[n]` 可以提到求和号外（每通道），组 32 的 `s[k//32]` 不行，要拆部分和、打断累加链——实测 2.0–2.4 倍变慢（176.3 → 73.4 TOPS），只换 1.55 倍精度。这就是 per-channel 的由来。
5. 布局：`torch._int_mm` 的 B 必须列主序，行主序**静默**退回慢路径（50.3 vs 205.8 TOPS）。`nn.Linear` 的 `[N, K]` 行主序权重取 `W.T` 天生就是列主序，别做 `contiguous()`。
6. `AI ≈ 2M`，屋脊点 274（规格）/ 323（实测）→ `M < 137`（或 162）必然带宽受限。harness 的 `M = 128` 正好卡在这里：地板 1.05 ms、实测 0.99 ms、139.4 TOPS = 68% 峰值就是上限；`M = 512` 才有 189.6。
7. `token/专家 = tokens_per_step / 32`，所以 batch size 直接决定可达 TOPS（4096 token/step → 128/专家 → 139 TOPS；16384 → 512/专家 → 190 TOPS）。
8. 2:4 在这张卡上不可用：bf16 cuSPARSELt 最好 1.47×（非 2×）、int8 0.12–0.98×（从未超过稠密）、无 Triton API、无 autograd；静态掩码当稠密 K/2 打能到 1.54–1.88×，但功能误差 23–68%（int8 现状 0.7–1.5%），所以否。
